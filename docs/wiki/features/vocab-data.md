# Vocab Data

## 목적

단어 데이터가 어떤 종류로 나뉘고, 런타임에서 어떻게 `StudyItem`으로 통합되는지 설명한다.

## 현재 제공 단어장

기존 2개 기본 단어장과 N5~N1 실용 단어장5개를 제공한다. 수준별 고유5,364개(620/767/1927/1194/856), 신규4,114개이며 선택한 모든 용법에 검토 예문을 제공한다. ID는 `jlpt-level-n5`~`jlpt-level-n1`이며 최신 수록 수는 `content/jlpt/progress.json`을 따른다. 신규 어휘 ID는 `lex-jmdict-<사전항목ID>`로 수준·정렬과 분리했다. 신규 어휘 묶음을 단계적으로 반영하고, 별도 참조 승인을 받은 고유 기존 ID도 수준별 목록에 연결한다. 동일 핵심 용법으로 독립 승인된27그룹의 학습 기록 연결을 활성화했다. 원본 단어와 예문은 보존한다. 단어장별 `wordIdPrefix`와 기존 ID는 원본 메타데이터로 보존한다.

확충 원고·사전 후보·검수·출처는 `content/jlpt`에 있다. 사전 후보 21,585개를 완성 어휘 수로 세지 않는다. `npm run jlpt:audit`가 원고와 실제 런타임 원본의 상태를 대조하며, `--require-target`은 현재 원장 해시에 연결한 독립 최종 범위 검토가 없거나 오래되면 실패한다. 공개 분류는 비공식 학습 수준 추정이다.

원고 파서는 표기·읽기 조합의 사전 인덱스를 한 번 만들고 재사용한다. 단어마다 전체 후보를 반복 탐색하지 않으며, 같은 조합에 여러 사전 항목이 있으면 여전히 명시적인 사전 ID로 뜻을 구분해야 한다. 가나 표제어와 중복된 사전 표기 때문에 한 항목을 여러 번 세지 않는 것도 검사한다.

2026-09-29에 `주제별 단어장`(`theme-core`)과 `비슷한 단어들`(`ComparingWords`)을 삭제했다. 원본과 런타임에서 소속 단어 22개, 비교 쌍 5개, 연결 용법 12개와 예문 24개를 함께 제거했다. 기본 단어장의 ID와 내용은 유지한다. 주제형·비교형 데이터 형식은 유지하며 현재 해당 데이터 배열은 비어 있다. 2026-10-02 별도 에디터 앱을 제거했으며 표 편집·xlsx 입출력·디렉터리 저장은 제공하지 않는다.

## 보관 단어장의 수준별 병합

2026-10-02 `동사대박살`(`AbsoluteVerb`)의 854개 항목 중 503개를 수준별 목록에 추가하고 351개는 기존/신규 대표와 중복되어 추가하지 않았다. `VocabularySet.archived`는 선택 메뉴에서만 제외하며 원본 소유·ID·콘텐츠·예문·기존 순서를 남긴다. 저장된 선택은 N5로 연결하고 오래된 세션은 원래 ID로 조회할 수 있다. 수준별 기존 범위는 불변이며 새 묶음만 읽기순으로 뒤에 붙인다.

`legacy/verb-consolidation.json`은 사용자 요청·현재 세션의 수준/중복 판단과 원본/대표 해시·전량 854개 처리·병합 전 게시 목록을 보관한다. `published-membership.json`의 `consolidationIds`는 기존 독립 참조 승인과 구분한다. 기존 단어·용법·예문 배열의 해시가 달라지면 병합 검토가 오래된 것으로 거부한다. 콘텐츠 수정·별칭 활성화·프로필 병합을 승인하는 경로가 아니다.

감사는 과거 독립 `finalSelection`을 원래 범위·원장 해시와 대조하고, 별도 `scope.membershipConsolidation.reviewHash`와 현재 전체 목록을 검증한다. 하나라도 실패하면 `complete` 및 게시를 차단한다. 새 단계에 과거 Astra 검토자 정보를 복사하지 않는다. 향후 콘텐츠/수록 변경 시 이 병합 검토와 최종 선정 범위도 새 내용에 맞게 갱신해야 한다.

일반 단어 엔트리. 기본, 주제형, 비교형 모두 이 타입을 바탕으로 움직인다.

## 데이터 생성 경로

- 어휘 원본: `src/features/vocab/editor-data/*`
- 런타임 데이터: `src/features/vocab/data/*`
- 생성 스크립트: `scripts/generate-vocab-data.mjs`

`editor-data`는 과거 경로명을 유지한 데이터 전용 입력이다. 승인·출처·삭제 이력에 연결된 원본 경로와 내용 해시를 보존하기 위해 이름을 바꾸지 않는다. `src/features/editor`, 별도 HTML/부팅 파일, 에디터 라우트, 브라우저 저장 API, xlsx 의존성은 제거했다. 실제 JSON·생성 데이터·ID·소속·목록 순서·버전·검토 원장은 그대로 보존한다. 원본 수정은 저장소에서 수행하고 생성·감사를 실행한다.

`model/sourceValidation.ts`는 기존 데이터 검사를 어휘 영역에 유지한다. 정규화·ID 재부여·파일 쓰기 없이 단어장/단어 ID와 접두사 중복, 소속, 명시적 참조, 비교 쌍, 난도 및 `validateLearnContent`를 검사한다. `jlptPilot.test.ts`는 원본과 생성 데이터의 내용·ID·순서 일치 및 검사 전후 원본 불변을 확인한다. 예문 개정과 버전 승인 경로는 기존 콘텐츠 도구를 따른다.

분할 로딩 산출물은 `data/learnContentIndex.ts`, `data/learnContentLoaders.ts`, `data/learnContentShards/`다. 용법 ID의 고정 해시로 128개 묶음에 나눠 새 단어 추가 시 기존 용법의 묶음 위치가 변하지 않는다. 가벼운 인덱스에는 본문·정답·번역을 넣지 않고 ID·버전·검토 상태·난도·복습 목록용 한국어 뜻·묶음 번호만 둔다. 전체 `learnContent.ts`와 함께 생성하지만 학습 앱은 인덱스와 동적 로더를 사용한다. 생성 시 앱과 동일한 검증기를 실행해 `learnContentValidation.ts`에 전체 검사 결과를 기록한다. 로더는 동시 요청을 합치고 최근 8개 묶음의 검증된 조회 맵을 보관한다. 브라우저 자체의 모듈 캐시는 별도로 유지되므로 전체 메모리가 8개 묶음으로 제한된다는 뜻은 아니다. 현재 카드의 다운로드·버전·구조 검사 실패는 기록을 지우지 않고 재시도 안내로 표시한다. 최종 전량 실제 코퍼스/프로필의 Chromium·모바일 화면 에뮬레이션 검증은 `content/jlpt/benchmarks/2026-10-01-browser-scale.md`를 따른다. 물리 휴대폰 성능 결과가 아니다.

## 뜻과 중복 관리

- 같은 기본 세트 안에서 일본어 표기와 읽기가 모두 같은 항목은 하나의 엔트리로 유지한다.
- 한 단어의 여러 용법을 따로 학습해야 하더라도 표기와 읽기만으로 구분할 수 없다면 뜻 필드에 합친다.
- 비교형은 한 단어가 여러 비교 쌍에 참여할 수 있으므로 같은 단어를 별도 ID로 둘 수 있다.
- 기본 단어를 삭제하거나 통합하면 `vocabularySets[].wordIds`의 참조도 함께 제거한다.
- 뜻 수정은 어휘 원본에 먼저 반영하고 생성 스크립트로 런타임 데이터를 동기화한다.

### 괄호 예시 작성

- 뜻을 구체화하는 대상이나 상황은 `(바닥을) 닦다`, `(비에) 젖다`처럼 필요한 조사까지 괄호 안에 넣는다.
- 서로 다른 조사가 필요한 예시는 `(입으로) 불다, (악기를) 불다`처럼 따로 적는다.
- 같은 조사로 나열하는 대상은 `/` 대신 `·`를 사용한다.
- `(의태어) 두근거리다`처럼 분류 설명 뒤에는 한 칸을 띄운다.
- 번역투 설명보다 실제 한국어 결합 표현을 우선한다.

## 수정 시 주의점

- 원본 데이터 구조를 바꾸면 런타임 selectors와 생성 스크립트도 함께 봐야 함
- 목록은 `StudyItem`, 학습은 용법·예문을 읽으므로 단순 JSON 수정으로 끝나지 않을 수 있음

## 표기와 읽기 검증

- 전체 단어장을 점검할 때는 일본어 표기와 읽기의 어미 일치, 사전 표제어·읽기 조합, 품사와 동사 자·타 구분을 함께 확인한다.
- 단독 표제어의 읽기는 연탁된 접미 형태가 아니라 독립된 읽기를 사용한다. 예: `箱`은 `はこ`.
- 사전마다 자·타 구분이 엇갈리는 동사는 기계적으로 바꾸지 않고, 분류가 명확한 항목만 수정한다.
- 어휘 원본을 수정한 뒤 생성 스크립트를 실행하고, 데이터 품질 테스트로 확정된 수정과 어미 일치를 회귀 검증한다.

## 문장 학습 콘텐츠

`LearnSense`는 기존 단어 ID를 참조하는 안정적인 용법 ID·버전, 대표 의미, 한국어 힌트, 혼동 표현 자료와 검수 상태를 가진다. `LearnExample`은 예문 ID·버전, 일본어 앞문장/정답/뒷문장, 활용형 읽기, 한국어 번역·강조 문자열, 난도와 검수 상태를 가진다. 기본형은 기존 단어 데이터에서 읽는다.

힌트의 `비슷한 단어` 표시는 기존 `LearnSense.confusions[].japanese`도 후보로 고려해 `editor-data/hintConfusions.json`에 선택한 1~2개를 저장한다. 선택 자료는 용법 ID·현재 버전과 비교 단어 목록을 가진다. 생성기는 참조/버전·1~2개 제한·빈 값·중복·자기 표제어/읽기를 검사한 뒤 `data/hintConfusions.ts`를 생성한다. 자료가 없거나 버전이 다르면 런타임은 기존 대비 표현을 사용하며 이때도 최대 2개로 제한한다. 大切(기존 大切だ 포함)→大事와 では→それでは는 최초 보완으로 보존한다. 같은 한자의 다른 읽기는 괄호로 구분한다. 기존 단어·용법·예문 ID·순서·버전·내용과 과거 독립 승인 해시는 수정하지 않는다. 이 화면 보완은 현재 세션의 편집이며 새 독립 콘텐츠 승인으로 표시하지 않는다.

전체 어휘의 혼동 후보는 `npm run hint:scan`으로 찾는다. 한국어 뜻의 구분자·활용 변형과 연결된 JMdict 번역이 후보 근거이며 자동 의미 승인이 아니다. 괄호 속 대상 명사는 독립 뜻으로 분리하지 않고, 형용동사 말미는 표제어와 읽기가 모두 `だ`로 끝날 때만 보정한다. `content/learn/hint-confusions-review.json`에 원본 해시·전체 범위·검토 그룹의 용법 ID 스냅샷·선택/제외/분할·편집 이유를 저장한다. 사전의 다른 뜻만 공유하는 후보와 한국어 동음이의어는 제외하고 다의어는 현재 출제 용법을 기준으로 연결한다. `partitions`는 일본어 표기로 묶고, 같은 표기의 복수 용법을 각각 나눠야 하면 `sensePartitions`에 정확한 용법 ID를 지정한다. 예를 들어 暗い의 공간 의미는 薄暗い, 심리 의미는 陰気와 각각 연결한다. 그룹에 없는 용법 ID는 생성 전에 오류로 거부한다.

화면에는 최대 2개만 표시한다. 생성 단계에서 현재 용법의 `preferredComparisons`, 한국어 뜻 조각의 겹침, 기존 작성 대비, JMdict 상용어 우선 표지와 `nf` 빈도 구간 순으로 정렬한다. 영어 공유 뜻의 개수나 후보 배열의 순서를 유사성으로 취급하지 않는다. 사전 우선 표지는 빈도의 보조 근거이며 실시간 사용량 통계가 아니다. 편집 우선순위는 긴 목록·다의어 등 76용법을 직접 대조해 지정했으며, 검토 후보에 없는 표현을 지정하면 생성이 실패한다. 전체 후보 판단과 근거는 검토 원장과 감사의 `provenance`에 보존한다. 앱에 전달하는 선택 자료 자체를 1~2개로 줄이고, 런타임에서도 자기 답·빈 값·중복을 제거한 뒤 최대 2개로 제한한다. 편집 우선 표현이 1개인 용법에 기존 대비를 추가하지 않는다. `semanticChecks`는 대조한 용법의 제외 연결이 다른 후보 근거로 다시 들어오는 것을 막는다.

`node scripts/build-hint-confusions.mjs --apply`는 검토된 그룹의 쌍방 비교를 후보로 정렬해 1~2개 선택 자료를 보완 원본에 쓰며 기존 단어·용법 원본은 쓰지 않는다. 미검토 그룹을 자동 거절하지 않고 남은 목록으로 보존한다. `npm run hint:audit`는 현재 보완 원본과 검토 결과의 일치, 전체 원본 해시/범위 및 그룹 스냅샷을 확인한다. 그룹에 없는 일본어 표기와 표기/용법 분할의 중복 지정도 오류로 거부한다. 생성 뒤 실제 힌트·예문 대조에서 잘못 연결한 쌍을 정정하면 해당 그룹에 이전 판단과 제거 근거를 `semanticCorrections`로 보관한다. `npm run hint:audit -- --require-complete`는 미검토 그룹이 남으면 실패한다. `output/hints/review-audit.json`은 전체 용법별 보완/미검토 그룹·연결 근거·자기 정답 필터의 제외 기록을 포함한다. 반영 개수와 전량 검토 완료는 별도 지표다.

원본 `editor-data/learnContent.json`을 생성 스크립트와 콘텐츠 도구가 읽는다. 생성 스크립트는 현재 원본이 있으면 인접 폴더의 레거시 단어장보다 우선한다. `content/learn/*.tsv`는 초기 개별 작문 자료이며 명시적인 import 도구로만 불러온다. prebuild에서 다시 가져와 현재 원본을 덮어쓰지 않는다. import는 항상 draft이며 검수 완료를 자동으로 주장하지 않는다.

예문 품질은 단어별 자연스러움, 유의어별 구별, 전체 문형·상황 다양성으로 검수한다. `node scripts/audit-learn-content.mjs --require-complete`는 전체 수록 여부와 문장 유사도 검토 대상을 확인한다. 유사도 수치만으로 검수 완료 처리하지 않는다. 문장 틀에 단어만 대입한 생성은 금지한다.

## 동일 의미 예문의 정리 (2026-10-02)

같은 용법의 장면·대상·활용형 차이만으로 예문을 여러 개 유지하지 않는다. 의미·뉘앙스·관용적 쓰임이 다르면 각 의미의 대표 예문을 남긴다. 기존 2,737개 복수 예문 단어를 대조하여 2,677개 단어에서 3,742개를 삭제했다. 전체는 5,635단어·5,658용법·5,874예문이며 190개 용법에 의미별 복수 예문이 남는다. 별도 용법 23개와 단어·용법 ID/버전은 그대로다.

의미별 묶음과 대표 ID는 `content/learn/example-pruning-review.json`, 삭제 원문·이유·전후 해시·원래 순서는 `content/learn/example-pruning/`에 보관한다. `node scripts/prune-learn-examples.mjs`는 검토한 전체 원본 해시, 빠짐없는 의미 분류, 그룹별 잔존 대표를 먼저 검사한다. `--apply`로 명시적으로 반영하며 마지막 예문 삭제·ID 재부여·순서 변경·본문 정정은 허용하지 않는다. 이력을 먼저 쓰고 원본을 쓰므로 중단 시 같은 검토본으로 재실행할 수 있다. 이미 반영한 작업은 다시 삭제하지 않는다.

생성·확충 감사·기존 원고 재가져오기는 삭제 이력을 역으로 검증한 원본으로 과거의 게시·참조·동일 용법 연결 승인을 대조한다. 현재 데이터와 삭제 원문의 합이 기존 승인 내용과 정확히 일치해야 한다. 옛 승인 해시나 독립 검토자 정보는 고쳐 쓰지 않는다. 실제 학습·준비 상태·예문 수는 삭제 후 현재 데이터로 판단하며 복원한 과거 원문은 검증에만 쓴다. 단어 선정 범위는 유지하고 삭제 이력 해시는 `progress.examplePruning`에서 별도로 검증한다. 기존 원고의 재가져오기는 삭제 예문을 부활시키지 않는다. 정리된 용법을 다시 문장 개정하려면 삭제 이력과 연결하는 명시적 후속 개정이 필요하다.

후리가나 보정 원천 `content/learn/furigana-overrides.json`은 현재 남은 예문의 ID·문장 부분·원문과 대조한다. 삭제된 예문에 대한 과거 보정 27개를 정리했으며 삭제 예문의 본문과 대표 연결 이력은 그대로 보존한다. 살아 있는 예문의 원문 불일치와 검증되지 않은 누락 보정은 계속 차단한다. 생성기는 검증된 삭제 이력의 ID만 현재 생성 대상에서 제외할 수 있고 삭제 예문을 되살리지 않는다. 진행 중 카드·undo의 복원은 `storage-and-share.md`를 따른다. 이 정책이 이전의 일괄 2·3예문 보존 정책을 대체한다.

## 검토된 예문 정정

### 목표어의 긍정 용례 (2026-10-05)

목표 뜻이 긍정인 단어의 대표 예문은 그 뜻을 직접 보여 준다. `正しい`의 정답을 `正しくない`로 쓰거나 `完全` 뒤에 `ではありません`을 붙이는 식의 부정·금지·불가능 용례는 긍정 문맥으로 정정한다. 정답 내부뿐 아니라 뒤 문장에 붙는 부정과 한국어 번역·강조 구간도 대조한다. `少ない`, `思わず`, `顔が立たない`처럼 표제어 자체의 형태·의미에 부정이 들어가는 단어는 유지한다. 주변 문장의 부정이나 사물의 소진·부재를 나타내는 명사 문맥을 일괄 금지하지 않는다.

사용자의 이번 명시적 요청에 따른 60개 정정은 `content/learn/example-corrections/2026-10-05-positive-target-examples.json`에 전체 용법 전후 원문·해시·정정 사유와 현재 세션의 편집 검토로 기록했다. 단어·용법 메타데이터, ID·소속·순서·난도·개수를 유지하고 바뀐 예문의 버전만 정확히 1 올렸다. 과거 Astra 독립 승인을 고쳐 쓰거나 새 독립 검토로 표시하지 않는다. 상세 비교는 [정정 보고](../../../content/learn/positive-target-examples-review.md)를 따른다.

`scripts/lib/reviewed-example-history.mjs`는 현재 원문과 정정 결과의 일치, 전후 해시, 버전 증가, 불변 메타데이터와 번역 강조 구간을 확인한다. 감사용 입력에서만 정정을 역으로 돌린 다음 기존 삭제 이력을 검증해 과거 게시·별칭·참조 승인을 대조한다. 병합 승인은 삭제 이후·이번 정정 이전의 정확한 원본과 대조한다. 현재 정정 원문으로 런타임을 생성하며 삭제 예문을 되살리지 않는다. 삭제된 카드의 대체 예문 버전은 검증된 현재 버전으로 연결한다. 옛 원고를 다시 가져와도 정정된 예문을 덮어쓰지 않는다. `progress.exampleCorrections`에 이번 이력의 해시와 범위를 별도로 표시한다.

이 경로는 이번 예문 극성 정정 이력에 한정한다. 삭제 후 새 정리·단어 뜻 변경·용법 추가와 기존 독립 개정 도구의 승인 조건을 대체하지 않는다. 예문 변경을 포함한 옛 진행 카드는 기존 버전 검사로 판정을 차단하고 용법 프로필·예정일은 유지한다.

단어 뜻·용법·ID를 그대로 두고 문맥만 고치는 경우 `pilot/example-versions.json`에서 바뀐 예문의 버전만 1 올린다. 원고를 다시 검토하고 새 해시 승인을 받은 뒤 `jlpt:pilot -- --publish --revise=<단어ID목록>`으로 명시한 항목만 바꾼다. 실제 편집 내용이 이전 게시 해시와 다르면 덮어쓰지 않는다. 단어/용법 메타데이터·예문 ID·순서·개수 변경, 버전 미증가·건너뛰기, 문맥 변경 없는 버전 증가는 이 경로에서 거부한다. 용법 버전과 숙련도·예정일을 유지하며 진행 중인 옛 예문은 판정을 차단한다. 단어 의미 변경은 별도의 기록 이전 설계가 필요하다.

기존 단어 이전의 대조 자료는 `node scripts/audit-jlpt-legacy.mjs`로 재생성한다. 고정 기준본 ID의 현재 존재 여부, 표기·읽기 중복 그룹, 후보 사전의 다중 일치/미일치, 검토 예문 3개 미만 용법을 과거 기준의 참고 지표로 집계한다(현재 최소 1개 정책의 미완료 판정은 아니다). 산출물은 `output/jlpt/legacy-mapping-audit.json`이며 검토 후보일 뿐이다. 이 검사로 뜻이 같은 별칭이라고 자동 승인하거나 프로필을 합치지 않는다.

완료 배치의 검토 원장은 `npm run jlpt:accept -- n3-001`처럼 통합한다. 각 words 파일에 대응하는 모든 review 파일이 있어야 하며, 단어 ID·개수·중복·현재 draft 해시·Astra high 검토·기존 승인 충돌을 먼저 확인한다. 하나라도 불일치하면 원장을 쓰지 않는다. 이 명령은 새 승인을 연결할 뿐이며 원고 재생성, 앱 반영, 전량 감사는 별도로 수행한다.

`sync-reviewed-jlpt.mjs`는 실제 앱 원본을 바꾸기 전에 신규 원고의 예문을 현재 전체 코퍼스 및 동시 인도된 신규 원고와 대조한다. 신규 예문을 포함한 높은 유사도 쌍이 있으면 승인 통합·앱 반영을 중단하고 `output/jlpt/prepublication-similarity.json`에 검토 대상을 남긴다. 독립 검토와 장면 정정을 마친 원고만 다시 반영하며 이미 게시한 예문 정정은 별도의 명시적 버전 개정 경로를 따른다.

가져오기 파서는 사전 leading sense에 명시된 Ichidan/Godan 외에 suru/Kuru 불규칙 동사도 3그룹으로 지원한다. `noun ... suru` 표제어는 임의로 동사로 다시 붙이지 않으며, 허용 읽기에 있는 가나 표기는 한자 표기 대신 사용할 수 있다.

## 기존 단어 참조 기반 준비

`VocabularySet.membershipMode = explicit`은 다른 기본 단어장의 기존 ID를 `wordIds`에 참조할 수 있는 저장 계약이다. 기본 단어장 조회는 이 목록 순서를 따른다. 원본 단어의 `setId`·ID를 바꾸거나 전체/즐겨찾기에 복제하지 않는다. 정규화와 JSON/TS 저장은 기존 참조 순서를 유지하고 새 소유 단어를 뒤에 붙인다. 이 순서는 저장된 학습 범위의 기준이다.

고유 기존 ID 6개의 독립 참조 승인 후 N3·N2에 explicit 모드를 처음 활성화했다. 기존 단어·용법·예문은 바꾸지 않으며 추가 승인을 받은 ID만 뒤에 연결한다. 당시 에디터 검증 기록은 `content/jlpt/reference-editor-verification-2026-09-30.md`에 역사적 근거로 보존하며 현재 앱 기능을 뜻하지 않는다. 실제 참조를 대상으로 기존 단어장에서 만든 학습 프로필을 수준별 단어장에서 이어 쓰고 판정·undo 후 같은 프로필·예정일로 돌아오는 것도 확인했다.

고유한 기존 ID의 참조 게시에는 `legacy/membership-reviews.json`의 명시적인 `legacy-reference-publication` 승인(Astra high, 수준·원본 내용 해시·시각·검토 메모)이 필요하다. 이전 분류 제안 승인은 이를 대신하지 않는다. 가져오기는 기존 단어·용법·예문을 바꾸지 않고 수준별 목록에 ID만 추가한다. 중복 정규형/별칭 그룹은 이 경로에서 거부하며 별도의 기록 이전이 필요하다.

`pilot/published-membership.json`은 마지막 게시 목록과 기존 참조 ID를 기록한다. 신규 묶음 사이에 기존 참조가 추가되더라도 이미 게시된 순서를 유지하고 새 단어는 끝에 붙인다. 원본에서 순서가 달라졌거나 승인된 참조·신규 목록과 기록이 어긋나면 덮어쓰지 않는다. 감사는 게시된 목록, 참조 승인 해시와 explicit 소속 방식을 함께 확인한다.

확충 가져오기와 런타임 생성은 동일한 내용의 파일은 다시 쓰지 않는다. 변경 파일은 같은 디렉터리의 임시 파일을 완성한 뒤 교체한다. Windows 공유/잠금 오류는 짧게 최대 3회 재시도하고, 계속 실패하면 기존 파일을 보존한 채 오류를 반환한다. 파일별 교체이며 여러 파일 전체의 단일 트랜잭션은 아니므로 실패 후에는 생성을 다시 완료하고 두 콘텐츠 감사를 확인해야 한다.

기존 어휘의 후속 편집 입력은 `node scripts/prepare-jlpt-legacy-work.mjs`로 만든다. 원본1,508개 ID와 용법/예문 및 연결 사전 근거를 1,385개 표기·읽기 그룹, 47개 파일로 나누어 `output/jlpt/legacy-work`에 저장한다. 각 원본 내용 해시와 파일 명세가 있으며 동일 표기·읽기가 같은 뜻이라는 승인은 아니다. 수준 배정·예문 보강·별칭 판정은 별도 검토를 거쳐야 하고 생성 명령은 원본이나 학습 기록을 수정하지 않는다.

기존 수준 제안은 `content/jlpt/legacy/assignments-NNN.json`에 보존하고 `node scripts/audit-jlpt-legacy-assignments.mjs NNN`로 원본 해시·원본 ID 전량 포함·사전 근거·수준/미해결 근거·별칭 후보 ID를 검사한다. 이 구조 검사는 편집 승인이나 프로필 이전을 수행하지 않는다. 원본이 바뀌면 재검토하며 미해결 수준을 임의로 채우지 않는다.

기존 사전 연결이 없고 na_adj 표제어와 읽기가 모두 `だ`로 끝나는 경우만 말미를 뺀 기본형을 추가 검색한다. `legacyMatchEvidence`에 원본과 검색형을 남기며 원본 단어·읽기·내용 해시는 유지한다. 생산적 수량 표현이나 복수 읽기 괄호 등의 다른 미일치는 자동 변형하지 않고 후속 검토로 남긴다.

기존 ID 연결이 없으면 사전의 대체 표기·가나 표기와 읽기가 원문에 정확히 맞는 후보도 조회한다. 서로 다른 동음이의어 후보는 모두 제시하며 뜻을 자동 선택하지 않는다. 3그룹 동사이고 표제와 읽기가 모두 `する`로 끝나며 사전 기본형에 suru 명사 품사가 명시된 경우만 해당 기본형을 근거 후보로 제공한다. `する` 자체나 모든 명사를 임의로 동사화하지 않는다. 이 조회는 편집 근거를 보강할 뿐 수준/뜻 승인이나 원본 정정을 수행하지 않는다.

신규 어휘 수는 형용동사 말미 `だ` 유무를 같은 어휘로 집계한다(품사 na_adj이고 표기와 읽기 모두 해당할 때만). 이 보정으로 기존 13개 항목은 수준별 수록 수에는 남지만 신규 수에서는 제외된다. 기존 게시 ID는 별칭/기록 이전 검토 전까지 보존하고, 이후 새 항목의 동일 기본형 충돌은 가져오기에서 거부한다. 명사·표현의 마지막 글자를 임의로 제거하지 않는다.

## 2026-09-30 생산 효율 및 계측

`progress.complete`와 `remaining`은 현재 원장에 연결한 콘텐츠 선정·데이터 감사 범위다. `completionScope`에 이 경계를 명시한다. 전량 회귀 검사·브라우저 성능·실제 게시 성공은 별도 검증 기록으로 확인하며, 미선정 후보의 보류를 완료된 콘텐츠의 잔여 작업으로 표시하지 않는다.

같은 날 사용자 지시로 12,000개/신규 10,000개 하한을 폐기했다. 2026-10-01 후속 지시로 `content/jlpt/scope.json`의 목표를 수준별 단어장 전체의 고유 어휘 약 5,000개로 조정했다. 4,750~5,250개는 내부 계획 범위이며 할당량이 아니다. 진행 집계는 신규 수를 계속 분리하며 수량만으로 완료하지 않는다. `finalSelection`에는 Astra high의 수준별 범위 설명·미해결 누락 없음·선정 이유·확정 수량·현재 `selectionSourceHash`가 필요하다. 수량 또는 원장이 달라진 오래된 최종 검토는 거부한다. `--require-target`은 이 콘텐츠 범위 검토까지 요구하며 성능·배포 검증은 별도다.

대표 용법별 검수 예문 최소 1개를 허용한다. 기존 예문과 ID·버전·프로필은 보존한다. 신규 작성은 Sol medium 두 담당이 서로 다른 묶음의 어휘+예문을 맡고 Astra high가 전량 검토한다. 메타데이터 저장 직후 `preflight-jlpt-batch.mjs <batch> <part>`, 원고 저장 후 `--examples`로 사전 연결·품사·필수 항목·기존 중복·가린 문장 중복을 검사하고 오류를 한꺼번에 반환한다. 의미·품사 적절성과 자연스러움은 독립 검토로 확인한다.

검토자는 `record-jlpt-review.mjs <batch> <part> --prepare`로 현재 원고 snapshot을 만들고 전량 확인한 뒤 `--accept=<snapshotHash>`로 명시적으로 승인한다. 이때만 해시·모델·시각과 간결한 공통 메타데이터가 자동 기록되며 수정 항목은 corrections 파일에 별도 남긴다. `accept-jlpt-batch.mjs`는 이전 배열 원장과 새 compact 원장을 모두 검증하고, sourceHash가 달라지면 거부한다. `--part=NN`은 명시한 완료 부분만 통합하는 선택지이며 기본값은 기존처럼 전체 배치 필수다.

측정 범위와 기준본은 `content/jlpt/benchmarks`에, 담당별 시각과 검사 시간·오류는 해당 batch에 기록한다. 준비/생산/검토/반영 시간, 실제 승인 단어·예문 수, 수정률, 산출물 바이트를 구분한다. 예전 단계별 시간이 없으므로 개선 배수나 비용 절감률을 추정하지 않는다. 기존 미완성 배치와 legacy 작업은 측정 표본에서 제외한다.

후보 탐색은 `node scripts/list-jlpt-candidates.mjs n4 --count=100 --offset=0`으로 현재 원본·기준본·모든 작성 배치·pilot에 있는 사전 ID 및 정규형을 제외한 근거 자료를 만든다. 이 자료는 후보이며 수준/품사/의미 승인이나 예약이 아니다. 저장 뒤 preflight를 다시 실행하고 같은 ID의 본인 승인 pilot 항목을 새 충돌로 오인하지 않는다.

`unassigned --evidence-level=N5`처럼 원래 출처에 특정 등급이 연결된 미확정 후보만 좁힐 수 있다. 여러 표기·뜻의 등급 충돌을 해소하거나 수준을 자동 배정하지 않으며 모든 등급 근거를 출력에 유지한다. 결과 파일명에도 근거 등급을 넣어 다른 후보 조회를 덮어쓰지 않는다.

실용성·독립 단어 적합성 등으로 제외한 후보는 배치 `selection.json`의 `excluded` 배열에 `dictionaryId`와 사유를 기록한다. 후보 조회는 이 ID를 기본 제외하며, 명시적인 재검토 때만 `--include-excluded`로 다시 포함한다. 편집자가 보류한 후보를 수량 부족 때문에 반복 제시하지 않는다.

계속 생산 중인 완료 묶음은 `node scripts/sync-reviewed-jlpt.mjs --check`로 아직 전역 원장에 연결되지 않은 검토 파일만 조회한다. 옵션 없이 실행하면 기존 검토 파일에 대해 원래 accept 검증을 수행하고, 모든 현재 원고의 승인을 검증한 뒤 로컬 원본·런타임을 갱신하고 전체 콘텐츠 감사를 실행한다. 새 편집 승인을 만들지는 않는다. 진행 중 reviewer의 원고 추가로 승인 대조가 어긋나면 게시 전에 실패하며 새 승인 기록이 준비된 후 다시 실행한다. 수량·예문 증분 및 감사 결과는 `content/jlpt/integration-log.jsonl`에 남긴다. Git push나 외부 게시를 수행하지 않는다.

검토 중 수준 근거가 부족한 항목은 배치의 `held-NN.json`에 기존 단어 정보·원고 전체·사유·권장 수준을 보존한다. 후보 조회는 기본적으로 보류 ID를 제외해 같은 수준으로 다시 쓰는 일을 막는다. 적절한 수준으로 명시적으로 재검토할 때만 `--include-held` 또는 보류 원고를 사용한다. 승인 단어 수에 보류 항목을 포함하지 않는다.

## 검토된 별칭 활성화

`legacy/alias-pilot-review.json`은 의미 검토, `legacy/active-aliases.json`은 명시적인 활성 대상이다. `buildReviewedAliases`는 Astra high의 동일 핵심 용법 이전 승인과 모든 구성원의 현재 원본 해시를 확인한다. 생성 결과 `data/learnAliases.ts`만 런타임에서 사용한다. 분류의 별칭 후보나 표기 일치만으로 활성화하지 않는다. 大切·簡単은 대표 의미 범위가 더 넓어 이전을 보류했다. 원본 콘텐츠·ID·단어장 순서와 옛 세션 조회를 유지한다. 확충 감사는 활성 승인을 재검증하고 최종 범위 검토 해시에 별칭 검토·활성 목록을 포함한다.

`prepare-jlpt-alias-work.mjs`는 현재 정규형 중복과 분류에서 명시한 별칭 후보 관계를 연결해 원본 단어·용법·예문·수준 참조·분류 근거를 10그룹씩 제시한다. 전이 관계나 표기 일치만으로 의미 동등성을 승인하지 않는다. 기존 원본·학습 기록을 바꾸지 않으며 검토자는 모든 구성원을 대조해 대표·권장 수준·동등성 또는 보류 이유를 판단한다. 현재 기록 연결은 구성원마다 용법1개인 동등 핵심 용법만 지원한다.

검토되어 활성화된 그룹의 기존 대표 ID를 수준별 목록에 넣으려면 별도의 `legacy-reference-publication` 승인에 `aliasGroupId`를 명시해야 한다. 가져오기와 감사는 같은 원본에 대해 `buildReviewedAliases`를 먼저 실행하고, 그 결과로 참조 승인을 검증한다. 비대표 구성원, 비활성 그룹, 미검토된 같은 정규형의 제3항목, 별칭 승인만 있고 수준 참조 승인이 없는 항목은 넣지 않는다. 이미 게시된 순서는 유지한다. 다른 의미를 갖는 후보의 기록을 이 경로로 억지 통합하지 않는다.

같은 정규형의 기존 항목이 서로 다른 핵심 용법이면 `duplicateSelection.policy = distinct-core-usages-no-profile-transfer`로 수준별 대표 하나만 선택할 수 있다. 같은 참조 승인 안에 모든 정규형 구성원의 원본 ID·전체 내용 해시와 독립 의미 검토 메모를 기록한다. 누락된 구성원·제3항목·변경된 원본·활성 별칭과의 겹침·중복 수준 참조는 거부한다. 이 경로는 별칭을 만들거나 프로필을 이전하지 않는다. 원본 단어와 서로 다른 학습 기록은 그대로 남고, 대표에 추가한 별도 용법은 새 프로필로 학습한다.

## 기존 원본의 예문만 개정

신규 pilot 이외의 기존 원본은 `scripts/revise-legacy-examples.mjs`로 개정한다. 제안의 `oldExample`은 현재 원문 전체와 같아야 하며 독립 검토를 마친 `proposedExample`만 게시용 draft에 넣는다. `--prepare <proposal.json>`은 전체 단어·용법 before/after와 해시를 기록할 뿐 앱을 바꾸지 않는다. 별도 Astra high 최종 검토의 `legacy-example-revision` 범위, 현재 draftHash, 검토 시각·메모가 있어야 `--apply <draft.json> <review.json>`을 사용할 수 있다.

단어·용법 메타데이터·ID·개수·순서는 그대로이고 변경 예문 버전만 정확히1 증가한다. 기준본의 기존 ID만 허용하며 이미 수준별 참조 승인 또는 활성 별칭에 쓰인 ID는 해당 승인 갱신을 따로 검토하도록 거부한다. 현재 내용과 검토 원본이 다르면 덮어쓰지 않는다. 모든 내용 구조 검사와 현재 해시 재확인 후 `legacy/revisions/<id>.json`에 원본·결과·승인을 먼저 기록하고 learnContent 한 파일을 교체한다. 중단 시 같은 승인만 재시도할 수 있고 이력만으로 적용 완료라고 주장하지 않는다. 감사는 연결된 전체 개정 이력과 현재 최종 내용을 대조하며 미적용·변조를 오류로 처리하고 최종 선정 해시에도 포함한다.

적용 후 런타임을 재생성하고 전체 감사를 실행한다. 기존 분류 입력에 있던 원본 해시도 달라지므로 해당 입력을 갱신하고 필요한 분류/참조 검토를 다시 받아야 한다. 옛 분류 승인을 새 해시로 기계 교체하지 않는다. 예문만 개정하면 기존 용법 프로필/예정일은 유지하며 바뀐 예문이 포함된 진행 카드는 기존 버전 검사로 판정을 차단한다.

참조 보류 수정 입력은 `prepare-jlpt-legacy-fixes.mjs`로 현재 원본과 사전 근거를 함께 모은다. 당시 보류 해시의 유효성과 기존 참조 승인 여부를 표시하며 제안 작성만 돕는다. 핵심 뜻 변경이나 용법 추가는 예문만 개정하는 경로를 사용할 수 없다. 승인 원장 통합도 기존 생성 파일과 같은 임시 파일 교체·제한 재시도를 사용한다.

## 기존 핵심 용법을 보존한 설명 정정과 용법 추가

`revise-legacy-content.mjs --prepare <proposals.json>`은 단어 뜻/자타 정보 정정, 같은 핵심 뜻의 용법 설명·힌트·대비 정정, 별도 중요 용법 추가를 전체 before/after 초안으로 만든다. 독립 검토된 상태만 허용하며 무변경 행은 제외한다. 기존 표기·읽기·품사·소속·순서·ID와 용법 버전은 불변이다. 기존 예문은 삭제/재배열하지 않고 정정할 때만 버전1 증가, 별도 용법과 예문은 새 ID/버전1로 추가한다.

`legacy-content-revision` 최종 승인에는 현재 draftHash 및 각 단어의 모든 기존 senseIds에 대한 `preserve-existing-core-usage` 판단과 근거가 필요하다. 이 의미 판단은 자동 검사가 대신하지 않는다. 기존 핵심 의미가 달라지면 이 경로에서 보류하며, 이전 숙련도를 더 넓은 의미에 옮기지 않는다. 단순 힌트 정정으로 기존 용법 버전을 올려 프로필을 버리지 않는다. 새 용법의 프로필은 독립적이고 기존 예정일·숙련도는 유지한다.

`--apply <draft.json> <review.json>`은 원본과 별도 참조/별칭 승인 여부를 확인하고 `legacy/content-revisions`에 원문·수정문·승인을 먼저 저장한 뒤 단어/용법 두 파일을 각각 교체한다. 전체 원자 트랜잭션은 아니므로 중단 시 원본 또는 승인 결과와 정확히 같은 파일만 동일 이력으로 재시도한다. 다른 수정은 덮어쓰지 않는다. 전체 감사는 둘 다 최종 결과와 같아야 통과하며 이력도 최종 범위 검토 해시에 포함한다. 적용 뒤 런타임과 분류 입력을 생성하고 변경된 기존 분류는 다시 검토한다.

## 미공개 중복 참조 복구

미공개 중복 수준 참조2개(AbsoluteVerb_162 いる, AbsoluteVerb_239 見付ける)만 별도 독립 승인·현재 원격 공개 기준 대조·전후 이력으로 철회했다. 원본 ID·콘텐츠·프로필 및 나머지 상대 순서는 보존했다. 일반 가져오기의 추가 전용 규칙은 바꾸지 않았고 기존 공개 JLPTN3_115 참조를 유지했다. 이 좁은 복구를 일반 삭제 권한으로 사용하지 않는다.
