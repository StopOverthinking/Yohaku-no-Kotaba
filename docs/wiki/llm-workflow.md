# LLM Workflow

이 문서는 Codex가 이 저장소에서 따라야 하는 기본 절차다.

## 필수 순서

1. 코드를 검색하거나 열기 전에 `docs/wiki/INDEX.md`를 읽는다.
2. 이 문서와 `docs/wiki/current-state.md`, 작업 대상 기능 문서를 읽는다. 저장·검증 변경이면 해당 계약 문서도 읽는다.
3. 문서에서 대상·계약을 좁힌 뒤 관련 코드만 확인한다.
4. 관련 테스트를 확인하고 변경 유형에 맞는 검증을 실행한다. 명령과 게시 전 필수 범위는 `testing-rules.md`를 따른다.
5. 구현이 끝나면 바뀐 설계를 위키에 반영한다.

## 탐색 범위 좁히기

- 문서 → 관련 코드 → 관련 테스트 순서로 확인한다. `rg`는 대상 기능·파일·심볼로 범위를 좁혀 사용하고 필요한 문맥만 읽는다.
- 일반 코드 탐색에서 `src/features/vocab/editor-data`, 생성된 `src/features/vocab/data`, `content` 전체를 한꺼번에 검색하거나 읽지 않는다. 이 경로에는 대량 코퍼스·생성 파일·승인 이력이 있다.
- 콘텐츠 작업은 기능 문서의 원본 경로와 정확한 단어·용법·예문 ID부터 찾는다. 연결된 이력·승인만 좁혀 확인하며 전량 감사가 필요한 작업은 기존 감사 도구를 사용한다.
- 생성된 TypeScript를 직접 수정하지 않는다. 데이터 원본이나 생성기를 수정하고 `npm run extract:vocab`으로 동기화한 뒤 관련 검사·콘텐츠 감사·게시 전 전체 검증을 수행한다. ID·소속·순서·버전·승인 이력은 보존한다.

## 코드 보기 전 체크

- 이 작업이 어느 기능에 속하는가
- 저장 구조가 바뀌는가
- UI 원칙을 건드리는가
- 테스트 기준이 달라지는가
- 미완 기능인 `탭 매치 러시`와 섞이지 않는가

## 기능 문서 선택 가이드

- 홈, 라우팅, 전역 레이아웃: `features/app-shell.md`
- 단어장과 데이터 모델: `features/vocab-data.md`
- 목록: `features/list-mode.md`
- 일반 학습: `features/learn-mode.md`
- 공유: `features/share-panel.md`
- 설정: `features/preferences-and-debug.md`

## 위키를 먼저 보는 이유

- 이 프로젝트는 UI 설명 문구가 적고 아이콘 중심이라 의도 파악이 어렵다.
- 저장 방식이 기능마다 다르다.
- 최근 세션에서 바뀐 판단 기준이 코드 여러 곳에 흩어져 있다.
- 미완 기능과 완료 기능을 분리해서 봐야 한다.

## 위키와 코드가 다를 때

1. 실제 동작과 테스트를 기준으로 현재 사실을 확인한다.
2. 구현을 수정할지 문서를 수정할지 결정한다.
3. 최종 상태에 맞게 둘 다 정리한다.
4. 변경 이유가 크면 `docs/wiki/current-state.md`에 현재 계약을 반영한다. 과거 정책·수량·검증·승인 기록은 [이력](current-state-history-2026-10-06.md)과 콘텐츠 원장에 보존하며 현재 상태로 다시 표현하지 않는다.

## 구현 후 반드시 갱신할 문서

- 라우트 추가/삭제: `architecture.md`, `features/app-shell.md`
- 저장 키/DB 변경: `storage-and-share.md`, 대상 기능 문서
- UI 원칙 변경: `design-rules.md`
- 세션 흐름 변경: 대상 기능 문서
- 우선순위 변경: `current-state.md`

## 금지

- 위키를 읽지 않고 바로 전역 검색부터 시작하기
- `탭 매치 러시` 코드를 기준으로 공통 설계를 추론하기
- 제거된 에디터 앱을 유지보수 대상으로 되살리는 설계
