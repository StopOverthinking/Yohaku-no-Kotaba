# Testing Rules

## 빠른 개발 검사와 게시 전체 검사

| 명령 | 범위와 용도 |
| --- | --- |
| `npm run typecheck` | `tsc -b`. 타입만 확인하며 데이터 생성·Vitest·감사를 실행하지 않는다. |
| `npm run test:quick` | 기본 전체 Vitest 구성에서 `jlptPilot.test.ts`와 `contextScale.test.ts`만 제외한다. 나머지 엔진·저장·DOM·스크립트 검사를 실행하는 개발 피드백용 명령이다. |
| `npm run check:quick` | 타입 검사 → 빠른 검사. 전량 코퍼스 순환·합성 규모·빌드·게시 감사를 포함하지 않는다. |
| `npm test` | 기존 전체 Vitest 검사. 전량 코퍼스 순환과 합성 규모 검사를 포함한다. |
| `npm run check:release` | 빌드 → 전체 Vitest → `audit:content` → `jlpt:audit -- --require-target`. Pages CI와 로컬이 같은 게시 검증 명령을 사용한다. |

`test:quick`은 제외 범위와 개발용이라는 안내를 출력한다. 빠른 검사의 성공으로 게시 완료나 콘텐츠 승인 완료를 판단하지 않는다. `check:release`의 빌드는 기존 `prebuild` 생성기와 JLPT 감사를 실행하며, 검증 후 릴리스 매니페스트 작성·업로드·배포는 CI의 별도 단계로 유지한다.

## 변경 유형별 필수 검증

| 변경 | 개발 중 확인 | 완료·게시 전 확인 |
| --- | --- | --- |
| 문서만 변경 | 현재 코드·원장 대조, 상대 링크와 과거 기록 보존 | 문서 사실 확인. 문서 변경만을 위한 앱 검사 반복은 필요하지 않다. |
| UI·목록·검색 | 관련 페이지·컴포넌트 검사, `check:quick` | `check:release`, 영향받은 키보드·포인터·좁은 화면의 실제 브라우저 확인 |
| 엔진·정책·저장·백업 | 관련 엔진·스토어·이전·실패·undo 검사, `check:quick` | `check:release`; 규모에 영향이 있으면 `contextScale.test.ts`와 전량 순환, IndexedDB·복원 변경은 실제 브라우저 확인 |
| 어휘·용법·예문 원본 또는 생성기 | `extract:vocab`, 관련 콘텐츠·생성·ID·버전·이력 검사 | `check:release`로 원본/생성 일치·전량 코퍼스·콘텐츠/최종 선정 감사 확인. 힌트 선택 변경은 `hint:audit -- --require-complete`와 `hint:display-audit`도 실행 |
| 검사 실행 환경·검증 명령·CI | 환경별 관련 검사와 명령/제외 범위 대조 | `check:quick`와 `check:release`, 전체 검사 범위·제한·게시 단계 보존 확인 |

빠른 검사는 생성·감사를 실행하지 않는다. 원본 변경 후 빠른 검사만 실행하거나 생성 TypeScript만 수정한 상태로 마치지 않는다. 자동 검사는 언어 자연스러움·의미 동등성·새 콘텐츠 독립 승인을 대신하지 않는다.

실용 어휘 확충의 콘텐츠 완료 경계는 `scripts/lib/jlpt-scope.test.mjs`로 확인한다. 잠정 수량 도달만으로 완료되지 않으며, 정당한 최종 선정은 잠정 범위 미만도 허용한다. 최종 검토의 원장 해시·수량·수준별 범위 설명과 미해결 누락을 검사한다. 이후 데이터가 달라지면 오래된 완료 승인을 거부한다.

## 기본 원칙

`verb-consolidation.test.mjs`는 동사 원본 전량 처리, 예문/단어 불변, 기존 수준별 숫자 범위 보존, 미분류·누락·가짜 중복·원본 메뉴 부활의 거부를 검사한다. `setMembership.test.ts`는 보관 단어장의 선택 제외·저장 선택 정규화와 원래 학습 ID 조회 보존을 검사한다. 기존 독립 최종 검토 검사는 병합 전 범위에 그대로 적용하며 새 병합 검토 해시와 실제 수록을 별도로 검증한다.

- 엔진, 스토어, 페이지는 각각의 성격에 맞게 테스트한다.
- 동작 규칙이 바뀌면 UI만 고치지 말고 엔진 또는 스토어 테스트도 같이 본다.
- 위키 문서가 테스트보다 우선하지는 않는다. 테스트와 실제 동작이 최종 사실이다.

## 테스트 위치

- 엔진: 각 feature 폴더의 `*.test.ts`
- 컴포넌트/페이지: 각 feature 폴더의 `*.test.tsx`
- 라이브러리: `src/lib/*.test.ts`

## 권장 검증 순서

1. 관련 feature 문서 읽기
2. 기존 테스트 확인
3. 구현 변경
4. 영향받는 테스트 수정 또는 추가
5. 관련 테스트와 `check:quick`으로 개발 피드백 확인 후 변경 유형별 필수 검증 실행

## 변경 유형별 테스트 기준

### 저장 구조 변경

- parse/load/save 경로 테스트
- 마이그레이션 테스트
- import/export 테스트

### 세션 흐름 변경

- 엔진 또는 스토어 테스트 우선
- 페이지는 핵심 인터랙션만 보강

### 목록/검색/필터 변경

- 렌더링 결과
- 숨김 동작
- 즐겨찾기와 검색 결합

### 성능성 UI 조정

- 재마운트 회피 여부
- `useDeferredValue`, `startTransition` 같은 흐름이 유지되는지 확인

## 수동 확인이 필요한 영역

- QR 카메라 스캔
- 실제 브라우저의 IndexedDB 동작
- CSS 체감 성능

## 실행 명령

명령별 범위는 문서 앞의 표를 따른다. 관련 파일만 실행할 때는 `npm test -- <test-path>`를 사용한다. 게시 전에는 `npm run check:release`를 실행한다.

## 대량 자료 검사 실행 조건

기본 테스트 환경은 JSDOM이다. DOM을 사용하지 않는 `scripts/lib/*.test.mjs` 14개와 `contextReviewPolicy.test.ts`, `contextScale.test.ts`, `jlptPilot.test.ts`에는 `@vitest-environment node`를 지정한다. UI·라우터·저장 등 나머지 검사는 기본 환경을 유지한다. 환경 분리는 검사 수·전량 코퍼스·시간 제한·작업자 수를 줄이지 않는다.

파일 교체 검사는 운영체제의 임시 디렉터리에 자체 작업 폴더를 만든다. Git에 포함하지 않는 `output/jlpt`가 존재한다고 가정하지 않으며 깨끗한 CI checkout에서도 같은 검사를 실행한다. 준비가 실패하면 정리 단계에서 미생성 경로로 추가 오류를 내지 않는다.

Vitest 동시 작업자는2개로 고정한다. 많은 CPU에서 전량 콘텐츠가 작업자마다 복제되어 생긴 부하성 시간 초과를 방지하며 기존 시간 제한은 유지한다. 중간 실제 규모 브라우저 측정은 `content/jlpt/benchmarks/2026-09-30-browser-scale.md`와 원자료를 따른다. 앱 스토어/IndexedDB 시간, 배포용 화면 페인트, 초기 이전/캐시 재방문을 구분한다. 합성 학습 기록·모바일 에뮬레이션·로컬 네트워크라는 경계를 명시하고 최종 수록 규모 확정 후 재측정한다.

- `scripts/lib/legacy-example-revision.test.mjs`: 기존 원본/용법 보존, 승인 누락·오래된 해시·별도 참조/별칭 보호, 버전 건너뛰기·의미 변경·중복 개정 거부, 미적용 이력과 연쇄 개정의 현재 내용 일치를 검사한다.
